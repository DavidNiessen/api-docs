# Editing JSON request bodies

JSON request bodies open in the raw **JSON** editor. For object schemas with declared properties, choose **Fields** to edit individual values. Strings use text inputs, password/write-only strings are masked, booleans and enums use selectors, and nullable properties have an explicit null control. Numbers retain their original JSON number tokens, including large integer IDs and precise decimals. Nested objects expand into their own controls, including referenced and recursive schemas. Homogeneous arrays expose item controls, including object items and nested arrays, with **Add item** and **Remove** actions. Each expanded object or array has a **Fields / JSON** switch; unsupported schemas use JSON within their field. Strings inside write-only objects and arrays remain masked in field controls.

Use the include checkbox to add or omit a property. New values use an explicit constant, default or example when available; otherwise the editor starts with an empty value of the declared type. Required labels remain visible. Unknown properties and existing read-only properties are retained when another field changes; edit those values through JSON. Read-only properties are excluded from the field controls. A `const` property displays its fixed value.

Incomplete numeric or collection edits disable **Send request** and replace the snippet with an error. The underlying body keeps its last valid value until the field input is valid. Returning to JSON discards incomplete field drafts and shows that last valid body. Switching an individual object or array between Fields and JSON discards incomplete drafts within that container; omitting it also clears its discarded errors. Adding or removing an array item discards incomplete drafts throughout that array before indexes change, while retaining valid values. Keyboard focus moves to the added or nearest remaining item, or the Add item button for an empty array. Valid edits preserve unrelated siblings, unknown properties and read-only values at every level. Field editing checks JSON syntax and the immediate declared value type; it does not replace full JSON Schema validation or the target API's constraints. Required fields, patterns, bounds and cross-field rules still apply.

## Precision and editing limits

Editing fields uses a JSON syntax tree rather than converting number tokens to JavaScript floating-point numbers. Updating a name does not round an unrelated ID such as `9007199254740993`, a precise decimal or an exponent value. Unknown nested values retain their numeric tokens too. Formatting and equivalent string escapes may change when the body is rewritten.

The field editor accepts at most 1 MiB of UTF-8 JSON, 32 JSON nesting levels and 10,000 values. Expanded controls share a budget of 100 fields/items across at most eight container levels, with at most 100 declared properties per object and 50 items per array. A nested container that exceeds these limits uses a local JSON editor while ordinary siblings remain editable. Composed/conditional schemas, ambiguous container type unions, tuple arrays, `items: false`, `contains`, `additionalItems` and `unevaluatedItems` also use JSON. Item defaults/examples initialize additions; required fields, uniqueness and item-count constraints remain the target API’s responsibility. Non-object roots and duplicate property names require the raw editor. These boundaries never truncate the request. OpenAPI 3.0 typed nullable fields and 3.1 null type unions keep their respective meanings.

## Sensitive examples

For JSON bodies, displayed/copied snippets replace values marked `writeOnly: true` or `format: password` with `YOUR_SENSITIVE_VALUE`, including referenced schemas, nested objects, array items and composition branches. Known credentials are also scrubbed from decoded JSON strings, so Unicode escapes cannot bypass a direct string comparison. Pattern and conditional schema branches are handled conservatively; a value may be redacted even when a specific branch would not apply. The redactor does not execute spec-supplied regular expressions.

Invalid, duplicate-key, oversized, excessively complex or unresolved JSON bodies use `YOUR_REQUEST_BODY` in snippets when safe redaction cannot be established. Redaction changes only the displayed example; the actual request uses the body you edited. The raw JSON editor displays the actual values for review. Response bodies are not covered by request redaction.

Annotations and known credentials cannot identify every secret. Mark sensitive schema fields, review copied requests and avoid entering production credentials in demo sites. Logical form-urlencoded inputs use schema-aware JSON redaction before encoding; literal encoded-form snippets omit the body. Other non-JSON body formats rely on known-credential replacement. Schema-aware JSON redaction is not an XML/form-data parser.

Programmatic clients can pass `{ schema, schemas, openapiVersion }` as the third argument to `redactRequest`, or call `redactJsonBody` directly. Generic request redaction without that context does not perform schema-aware body traversal. The public `parseJsonValue`, `serializeJsonValue` and `setJsonProperty` helpers in `@api-docs/contracts` preserve number tokens for integrations that build their own editors.

See [form-urlencoded bodies](form-bodies.md), [request serialization](request-serialization.md), [OAuth authentication](explorer-auth.md) and [generated snippets](snippets.md) for the remaining request behavior.

For binary files with text or JSON parts, use the [multipart editor](multipart-bodies.md). File selections stay separate from logical JSON values and generated source.
